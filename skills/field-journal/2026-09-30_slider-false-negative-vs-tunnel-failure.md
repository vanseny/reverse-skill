# 滑块"失败"的两种假象：判据假阴性 vs 出口隧道断

日期：2026-09-30
场景：zcode-api 批量注册（muse 别名入池），滑块自动求解 + 人工兜底

## 现象

一次运行里同时冒出三个"失败"信号，**全都是假的**：

```
❌ 面板关闭且拉不起，但文案无「通过」→ 判失败
⚠️ 找不到「点击开始验证」盒子: no start box   ×4
❌ 异常: Page.goto: net::ERR_TUNNEL_CONNECTION_FAILED at https://chat.z.ai/auth
```

实际结果是**成功**：`signup {"success":true}` → 激活邮件 → `✅ 成功 JWT=...`。

## 假象一：求解器判失败，但拖拽其实过了

`_solve_puzzle.py` 的 `_attempt()` 判据是**页面文案出现「通过/成功」**：

```python
if re.search(r"通过|成功|verified", str(get_lite(cdp).get("text") or ""), re.I):
    return True
```

这次面板关掉了、文案却读不到「通过」，于是返回 False，日志打「判失败」。

**但它是假阴性**，原因链条：

1. `_attempt()` 的 20 秒窗口**在文案出现之前就到期了**（面板 1s 就关了，之后
   一直 `no start box`）；
2. 外层 `solve()` 走到 312 行判失败 → 批次切人工等待；
3. **同一秒** `zcode_batch_reg.py` 的 hook 抓到了 `success 回调`；
4. 拿回调里的 param 提交，`signup` 200 通过。

所以**代价只是日志难听**，批次没白等（hook 是并行的、不受求解器误判影响）。
但诊断时极容易被这行日志带偏 —— 会以为滑块没过而去找定位问题。

### ⚠️ 当天晚些时候被证伪的一条（重要）

上面第 3 步一度写成「hook 回调是**唯一确定性**信号」，并据此认为"hook 兜底，
求解器误判无所谓"。**这个论断是错的**，同一天 `z2ch2vge` 就把它推翻了：

- 求解器连判 3 轮失败（三次拖拽落点分别在 gap 的 1px 内）；
- hook 随后抓到 `success 回调`，`param` 280 字符；
- **但提交被门禁吞掉，连 `/api/` 都没发出去。**

对比两个号留存的 param（base64 解出来结构完全一致）：

| 号 | certifyId | sceneId | 结果 |
|---|---|---|---|
| `vbdagzp8` | `mCEiCwJyIk` | `36qgs6xb` | signup 200 |
| `z2ch2vge` | `y3NxtD3iwd` | `36qgs6xb` | 门禁吞掉 |

所以 **`success` 回调只能证明"滑块控件自己认为过了"，不能证明服务端接受了
这个 param**。回调里带的 `certifyId` 是本次拖拽轨迹的产物 —— 轨迹不达标时，
控件照样回调，服务端在后续提交时才发现凭据无效（不回报错，直接静默吞）。

顺带证伪的另一个假设：曾怀疑"param 缺 scene 绑定导致门禁不稳"（因为 hook
日志一直打 `scene=None`）。**错**：`scene=None` 只是 hook 没抓到那个字段，
param 里 `sceneId` 明确是 `36qgs6xb`，两个号都一样。

**唯一确凿的判据只有 `signup {"success":true}`。** 在那之前的一切信号
（DOM 文案、hook 回调）都只是**必要不充分**。求解器判失败时，正解是重过一遍
滑块，而不是拿一个"看起来过了"的凭据去撞提交。

### 教训

- **判据假阴性 ≠ 操作失败。** 看到"判失败"先看有没有并行的**正向信号**
  （这里是 success 回调）把它兜住，别直接去修定位。
- **但正向信号也要分层且都不可全信**：DOM 文案（最弱）< hook 回调
  （次弱，只反映"控件自认过了"）< 服务端响应（唯一确凿）。文案读不到是
  **正常**的，不该作为"失败"的唯一依据；回调抓到也不算成功，**只有服务端
  接受了才算**。
- `_attempt()` 的窗口与 `solve()` 的重试之间，最好让 hook 参与判定，
  而不是全押在 DOM 上 —— 但 hook 参与的是"要不要停止等待"，不是
  "要不要宣布成功"。

## 假象二：出口隧道断，但报错长得像页面问题

`ERR_TUNNEL_CONNECTION_FAILED` 看着像网站/页面问题，实际是本地 bridge 的上游挂了：

```
chrome --proxy-server=http://127.0.0.1:18907
      └─ socks5_http_bridge.py  上游硬编码 = 198.44.166.196:3000 (1024 网关)
```

两个问题叠在一起：

1. 该 IP 在宿主 Clash 的 **DIRECT 规则**里（规则第一条）→ 被强制直连 →
   网关看到本机中国电信 IP → 403。见
   `2026-09-30_clash-direct-rule-hijacks-residential-gateway-egress`。
2. **协议也不对**：那个端口回 `b'HT'`（HTTP 代理），而 bridge 发的是 SOCKS5
   问候 —— 必然握手失败。

换成 `us.cliproxy.io:3010`（真 SOCKS5，问候回 `\x05\x02`；且不在 DIRECT 列表）
后立刻可用：经 bridge 出口 US/New Jersey/Verizon，`chat.z.ai/auth` HTTP 200。

### 教训

- **`ERR_TUNNEL_CONNECTION_FAILED` 先查本地代理链路，别去查目标站。**
  "TUNNEL" 指的就是本地到代理那一段。
- **不要在 bridge 里硬编码上游网关**。同一份 bridge 被多个脚本引用
  （zcode / muse / gmail），网关一换就是一片静默失败。至少要有启动自检：
  对上游发一次协议问候，协议不符就**拒绝启动**（这次是靠 `greeting=b'HT'`
  才定位到的）。

## 假象三：传输层 fetch 抛错，被下游判成"服务端拒绝"

同一天 `z2ch2vge` 重跑时又冒出一个假失败：

```
[net-err] /api/v1/auths/signup → TypeError: Failed to fetch
[net] None /api/v1/auths/signup
❌ signup 被拒:
```

看着像"服务端拒了注册"，实际是**代理抽风，响应没回来**。而且这个判断错得
很有欺骗性 —— 注意 `❌ signup 被拒:` 冒号后面是**空白**，那就是空 body 露的馅。

根因是 recorder 里**错误条目和成功条目字段不同却混进了同一个列表**：

```js
// 成功
window.__zrec.push({url, status, body, req, ts})
// fetch 抛异常
window.__zrec.push({url, err, ts})        // 没有 status / body
```

原判据只按 `"/api/" in url` 挑，于是错误条目也进了 `api_events`：

- 下游 `[e for e in resp if "auths/signup" in url]` 命中的是**错误条目**
  → body 为空 → `"success":true` 不匹配 → 报"被拒"；
- `if api_events: break` 也因为这条错误条目**提前跳出**，
  把本该重试的 `if errs:` 分支变成**死代码**。

**修法**：以"有没有 `status` 字段"作为"这是不是真响应"的判据 ——
有 `err` 的一律算传输层失败，不进 `api_events`。

### 教训

- **`Failed to fetch` ≠ 请求失败。** 它只说明**响应没回来**，请求很可能已经
  到达服务端并建号成功。`z2ch2vge` 就是活证：这一轮报 `Failed to fetch`，
  下一轮重跑同一个号，直接 `200 {"success":true}`，激活邮件也照常到。
  **遇到它应该重试，不该判死。**
- **区分"没发出去"和"发出去没回来"**：两者要从**客户端侧**判断 ——
  一条记录都没有 = 客户端门禁拦下（请求没发）；有 `err` 条目 = 已发出、响应丢。
  这两种情况的处置完全不同（前者要重过滑块，后者重试即可）。
- **给事件列表做过滤时，先确认候选条目的字段是齐的。** 把两种异构记录
  混进一个数组、再用宽松条件过滤，是这类静默误判的温床。

## 通用准则

**同一时刻出现多个"失败"信号时，先怀疑它们同源，而不是分别处理。**
这次四个信号里，两个是判据假阴性、一个是出口断、一个是响应丢 —— 但出口断是
真问题，判据假阴性和"响应丢被误判成拒绝"都是噪声。**先确认真问题（出口），
再看噪声是否要紧。**

**"失败"信号的可信度必须逐个标定，不能一概而论。** 本案例里四种信号的
实际可信度排序（由弱到强）：

| 信号 | 真实含义 | 可信度 |
|---|---|---|
| DOM 文案读不到「通过」 | 读不到 ≠ 没通过 | 最弱 |
| `success` 回调 | 控件自认过了，**不代表服务端收** | 弱 |
| `TypeError: Failed to fetch` | 响应没回来，**不代表请求没到** | 弱 |
| `signup {"success":true}` | 服务端确认 | **唯一确凿** |

**中间那两个"弱"信号是最危险的**：它们长得像结论（一个像成功、一个像失败），
但都只描述链路中的一段。判成功/判失败都必须落到**端到端的那一端**。
