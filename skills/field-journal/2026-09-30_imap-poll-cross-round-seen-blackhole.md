# IMAP 轮询里跨轮 `seen` 集合 + 邮箱硬上限 = 永久黑洞

- 日期：2026-09-30
- 场景：zcode 批量注册，等激活邮件（`fetch_verify_token`），600s 超时
- 结论：**同一封邮件、同一份代码，独立进程 1.2s 命中，长驻进程轮询 9 分钟不命中**

## 症状

批量脚本提交注册后进入等邮件循环，日志稳定每 5 秒打一行
`[IMAP] 等激活邮件… (Ns/600s)`，一路走到 600s 超时判定"无激活邮件"。
与此同时，另开一个一次性脚本扫同一个邮箱、同一个收件人，**1.2 秒**就取到了
那封邮件。邮件确实在，且 INTERNALDATE 显示它在等待开始前就已投递。

排查中排除了：限流（连续 600 次 FETCH 零错误）、文件陈旧（全盘只有一份，
mtime 早于运行）、收件人匹配（`alias.lower() in to` 成立）。

## 根因

```python
deadline = time.time() + timeout
seen = set()                      # ← 在 while 外面
while time.time() < deadline:
    ...
    total = <当前 INBOX 封数>     # ← 每轮重算
    for seq in range(total, max(0, total - 40), -1):
        if seq in seen: continue  # ← 序号被永久拉黑
        seen.add(seq)
```

两个因素叠加：

1. **2925 邮箱 INBOX 硬上限 300 封**。新邮件投递会驱逐最旧的，**序号被复用**。
   第 1 轮把 300..261 全塞进 `seen` 之后，新到的激活邮件恰好落在这些序号上，
   后续所有轮次全部跳过 —— 邮件一直在，代码永远看不见。
2. **激活邮件通常在提交后 10~40s 才到**，第 1 轮必然太早；而 `total` 每轮重算，
   序号右移后 `seen` 里的旧序号还会误伤真正的新邮件。

单轮内"序号去重"本身是合理的（避免同一封重复解析），错的是**把它跨轮记忆**。

## 修法

- 删掉跨轮 `seen`，改**每轮重扫全窗**，用 `Message-ID` 只在**单轮内**去重。
- 扫描窗口从"最近 40 封"扩到**全窗**（收件箱可能积压其它来源邮件，
  把激活邮件挤出窗口）。
- 顺手把"每轮 login/logout"改成**整个等待期复用一个 IMAP 会话**，
  异常时重开 —— 5 秒一轮的轮询原本会白做上百次认证。

```python
round_seen = set()                     # 每轮清空
for seq in range(total, 0, -1):        # 全窗
    ...
    mid = str(msg.get("Message-ID", "")).strip()
    if mid and mid in round_seen: continue
    if mid: round_seen.add(mid)
```

## 可迁移的经验

1. **任何"轮询 + 去重集合"的循环，先问集合的生命周期对不对。**
   去重集合的作用域应当是"一次完整扫描"，不是"整个等待过程"。
   跨轮记忆只在**被扫描对象的标识稳定**时才成立 —— 而按序号访问的邮箱、
   日志行号、分页游标，序号都会随新增/驱逐而漂移。
2. **IMAP 按序号轮询的固有问题**：序号不是稳定标识。能用 `UID` 就别用 `seq`。
   这次的 300 封上限让序号复用从"理论风险"变成"必然发生"。
3. **"独立跑得通、长驻跑不通"是状态污染的强信号**，优先怀疑跨轮累积的状态
   （集合、游标、连接、缓存），而不是网络或服务端。
4. 长驻进程的等邮件逻辑，**拆成一次性脚本**往往比修长驻进程更省事
   （本次即如此：先写了 `_finish_activation.py` 兜底，回头才定位到这里）。
